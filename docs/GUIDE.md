# webnovel-mcp 使用手册（从开书到完结）

> 一套「每天自动写一章网文、自动验收、你只管看报告」的写作流水线。
> 本手册面向使用者：从零装好、写出第一章、跑到全书完结，每一步做什么、在哪做、花多少时间。

---

## 1. 它是什么

三个部件，一条数据链：

- **MCP 服务**（本仓库）：书的仓库管理员。所有正文、大纲、设定、手记都存在你自己的设备上，带提交链，写坏的章能回溯。
- **两个专家**：`webnovel-coach`（写手，负责写章+自审）、`webnovel-reviewer`（质检员，只读，负责独立验收）。装进 WorkBuddy 的「我的专家」即可召唤。
- **三条定时任务**：每天 21:00 写作、22:00 验收、每周日 20:00 大纲体检。配置单见 [docs/AUTOMATION.md](AUTOMATION.md)，照抄即用。

关系：**定时任务到点唤醒专家 → 专家调用 MCP 工具写章、提交 → 验收专家复核 → 报告写进当日手记 → 你看报告。**

原则：设定和大纲由你拍板（创作决策机器不代劳）；正文日更全自动（写作决策机器代劳）。

## 2. 开始前你需要有

| 需要 | 说明 |
|---|---|
| WorkBuddy 环境 | 专家和定时任务跑在这里 |
| 一台能长期开机的设备 | 跑 MCP 服务：电脑、服务器、NAS、安卓手机都行，Node 18+ |
| 能连上服务的网络 | WorkBuddy 所在环境要能访问这台设备的地址和端口 |
| 一个 MCP token | 服务启动时设置，连接时填，别明文写进任何仓库文件 |

## 3. 五步上手（一次性）

**第 1 步 · 起服务**
克隆本仓库，装依赖（`npm install`），启动服务（`node server.mjs`，端口和 token 见 [docs/USAGE.md](USAGE.md)）。手机等特殊环境看 `scripts/` 下的部署脚本。

**第 2 步 · 装专家**
把两个专家包分别打包为 zip，在 WorkBuddy「专家中心 → 创建专家/导入」导入（推荐，全自动注册）。手动复制目录也可以，但**必须在 `~/.workbuddy/plugins/marketplaces/my-experts/.codebuddy-plugin/marketplace.json` 的 plugins 名单里各加一条**，否则 WorkBuddy 扫描不到，界面上永远搜不到。注意：如果以前装过同名 skill，先删掉，会和专家双触发。

**第 3 步 · 连通验证**
在对话里对写作专家说：「连上我的 webnovel 服务，跑一次状态检查」。它能报出服务版本和书库状态，就说明通了。

**第 4 步 · 开书**（见下一节，这是唯一需要你认真参与的环节）

**第 5 步 · 建定时任务**
照抄 `docs/AUTOMATION.md` 的三条配置单。**先别开定时**——手动触发跑两章（第 5 节），满意了再开。

## 4. 开一本新书（手动会话，约一到两次对话）

对写作专家说「我要开新书」，它会问你四个问题：

1. 书名
2. 题材（男频/女频/悬疑/科幻……不同品类它有对应写法）
3. 一句话故事（这本书讲什么）
4. 目标规模（多少万字、分几卷）

答完它会自动建好书骨架。然后陪你定三样东西：

- **设定集四篇**：世界观、主角卡、核心设定、关系主线。核心设定（比如金手指）**一定让专家把能力边界写成硬条款**——限制几米、耗什么代价、什么时候失效。这些条款是以后每章验收的对账依据，写含糊了后面必打架。
- **总纲 + 第一卷卷纲**：总纲定全书三幕和长线伏笔；卷纲定这一卷的节拍、伏笔埋收、卷末钩子。
- **前 10 章章纲**：每章写什么、冲突是什么、章末钩子是什么。章纲是动笔的前置条件，没有章纲系统不会动笔。

顺手做一件事：**把你的口味告诉它**——对话里说「记到风格记忆里」即可。比如「对话要口语化」「章末钩子必须狠」「别用成语堆砌」。之后每天自动写作都按这个口味来，不用重复说。

## 5. 先手动跑两章，再放手

1. 手动触发「写作」任务（或直接对话让 coach 写第一章）→ 读。
2. 不满意就说，改完让它把结论记进反馈记忆，再写第二章。
3. 手动触发「验收」任务 → 看验收报告长什么样。想测它灵不灵，故意把某章字数改短再验收，看它抓不抓得到。
4. 两章都过关 → 开启三条定时任务。从此日更全自动。

## 6. 日常使用

### 每天：系统自动，你 3 分钟

| 时间 | 谁 | 干什么 |
|---|---|---|
| 21:00 | 写作专家 | 读昨日验收报告的必修项 → 按今日章纲写正文 → 查重 → 自审 → 提交 → 写当日手记 |
| 22:00 | 质检专家 | 独立复核 8 项：字数、章号连续、AI 味词扫描、查重复跑、设定对账、事实链、手记闭环、读感抽读 → 报告写进手记 |
| 你 | 3 分钟 | 打开当日手记：看验收结论（通过/有条件通过/打回）→ 随机抽读几段正文 → 完事 |

报告有「打回」时：错别字、句式这类机械问题，写作专家第二天自己修；**设定级冲突**会标成「待作者决策」，这种当天处理——改设定集一句话的事，拖久了会污染后面所有章。

### 每周日：20 分钟到 30 分钟，补大纲

系统每周日自动清点「章纲库存还能撑几天」。提前量低于 20 章会提醒你。你只需和专家开个对话：按卷纲把下一批 10 章章纲敲定。**系统永远不会自己编大纲**——大纲断供时它会停笔写手记等你，绝不瞎写。

这个每周会话是整条流水线**唯一的固定人工成本**。

### 漏跑了怎么办

停机、断网、没电导致某天没写——**跳过，不补**。系统自动从当前状态续接，绝不一次补两章。事实链在盘上，丢不了。

## 7. 完结与下一本

- 最后一章提交完，全书走完总纲，流水线自然停摆（定时任务每天触发但发现没有下一章，只记一行手记）。
- 把这本书的三条定时任务停用或删除。
- 全书在 `books/<书id>/` 一个目录里，整目录拷走即得成品。发布前记得人工把查重复核一遍。
- 开新书：回到第 4 节。专家、服务、定时任务配置全部复用，只有定时任务里的书 id 要换。
- 想同时写两本：每本各建一组「写作+验收」定时任务即可，互不干扰。注意每本都要先手动过完第 4 节的设定期。

## 8. 使用守则

1. **设定和大纲必须你点头**——这是刻意的分工：机器负责执行，你负责方向。
2. **设定集边界写硬**：「大概很强」不行，「50 米、锁 3 个、强制下线」行。
3. **别跳过试运行**：前两章手动跑，是在校准之后两百章的口味。
4. **待作者决策项当天清**：攒着会烂。
5. **发布前人工查重**：自动查重是辅助，不是免检牌。

## 9. 边界（先说清，免得期望错位）

- 读感好坏机器判不了终审：验收报告只出建议，你每天的 3 分钟抽读就是终审。
- 查重引擎覆盖有限：能拦大段雷同，拦不住化用桥段，人工复核保留。
- 大纲不能无人值守生产：日更自动，扩纲必须你在场。

## 10. 出问题了

- **服务连不上**：先看服务进程在不在、地址端口对不对、token 是否一致；手机设备检查是否被省电策略杀掉（把服务加入电池白名单）。
- **写了一半服务挂了**：没提交的章等于没写，重启服务当晚自动重写，盘上数据零丢失。
- **验收天天打回同一类问题**：别改正文，去改设定集或风格记忆——源头修一次，以后每天都对。
- **想看某章的历史版本**：事实链带提交记录，用 `webnovel_query` 查任意章的提交轨迹。
